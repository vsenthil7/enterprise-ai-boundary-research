# Evidence Standard

## Claim labels

Every material statement should be marked as one of:

- **FACT** — directly established from an authoritative source or repository state
- **EVIDENCE** — observed support for a claim
- **ASSUMPTION** — working premise not yet proven
- **HYPOTHESIS** — proposition to test
- **DECISION** — adopted project rule or conclusion
- **OPEN QUESTION** — unresolved issue requiring research

## Evidence levels

- **E0 — Speculation:** unsupported idea or brainstorm
- **E1 — Plausible inference:** reasoned from known facts but not directly evidenced
- **E2 — Vendor / consultancy claim:** published by a party with possible commercial incentives
- **E3 — Named deployment:** identifiable organisation and use case in production or a documented pilot
- **E4 — Measured production evidence:** named deployment plus measured operational/economic outcome with credible methodology

## Confidence

Attach a confidence score from **0–100%** to material conclusions.

Confidence is not evidence. A high-confidence claim with weak evidence remains weakly evidenced.

## Counterevidence rule

For every significant AI-benefit claim, actively seek:

- evidence that ordinary software already solves the problem,
- evidence that pilots failed to scale,
- evidence that human review remains necessary,
- evidence that the economics are negative,
- evidence that deterministic architecture is retained underneath the AI layer.

## Mandatory challenge

Before accepting an LLM or agent use case, answer:

> **WHY NOT ORDINARY SOFTWARE?**

Possible deterministic alternatives include SQL, APIs, rules engines, schedulers, workflow engines, search, event-driven automation, traditional ML, scripts and standard application code.
